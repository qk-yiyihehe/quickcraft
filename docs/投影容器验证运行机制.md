# 投影容器验证运行机制

本文说明 QuickCraft 的 Litematica 投影容器验证功能如何运行，以及它和世界高亮、容器界面槽位提示、验证器列表悬浮预览、单个错误选择高亮、修正后自动取消之间的关系。

## 相关入口

- 配置开关：`QuickCraftConfigs.showLitematicaContainerVerifier` 控制验证器分类和世界高亮；`showLitematicaContainerSlotHints` 控制打开容器后的槽位提示。
- 核心逻辑：`QuickLitematicaContainerVerifier` 负责读取容器内容、比较槽位、生成颜色和槽位覆盖层。
- 验证器接入：`LitematicaSchematicVerifierMixin` 把容器错误并入 Litematica 原版 `SchematicVerifier`。
- 界面接入：`LitematicaGuiSchematicVerifierMixin`、`LitematicaWidgetListSchematicVerificationResultsMixin`、`LitematicaWidgetSchematicVerificationResultMixin` 负责按钮、统计行、分组和悬浮库存预览。
- 槽位高亮：`LitematicaHandledScreenSlotOverlayMixin` 在打开容器界面时画槽位底色、边框和缺失物品虚影。
- 配色：`QuickLitematicaVerifierPalette` 统一给世界高亮、列表文字、HUD 坐标、槽位底色和悬浮预览使用同一套颜色。

## 验证数据来源

原理图侧数据来自当前选中投影的 schematic block entity NBT。代码会把世界坐标反查到原理图 region，再取对应的容器 NBT、BlockState 和禁用槽状态。

实际世界侧数据分三种情况：

1. 单人/集成服：优先从真实世界的 BlockEntity/Inventory 直接读取。
2. 多人服务器：优先从 Litematica 的 `EntitiesDataStorage` 读取 Servux 或 OP 数据通道返回的 BlockEntity NBT。
3. 玩家打开容器后：从当前 `HandledScreen` 的槽位实时复制实际库存，用它刷新对应位置的验证结果。

多人服开始验证时，会先按本次原理图触碰的 chunk 批量请求容器 NBT。chunk 数据还没回来时，容器会进入 `pending`，验证器后续每隔一段 tick 继续复查这些位置。

## 容器错误如何分类

每个容器按槽位逐一比较原理图库存和实际库存：

- 原理图有物品、实际为空：缺失填充。
- 原理图为空、实际有物品：多余或错填，顶层归到错误填充。
- 两边物品类型不同：错误填充。
- 物品类型相同但数量不同：状态/数量错误。
- 合成器禁用槽状态不同：状态错误。

当前验证器主分类按钮是：

- 红色：错误填充。
- 蓝色：缺失填充。
- 金色：状态错误，包括数量不一致和合成器锁槽状态不一致。

紫色“多余填充”配色存在于槽位状态里，但顶层列表当前会并入红色错误填充分类。

如果一个容器没有任何槽位差异，`findMismatches` 返回空列表。空列表表示“已检查且正确”，不是待读取。

## 如何并入 Litematica 原版验证器

QuickCraft 在 Litematica 的 `MismatchType` 枚举里提前注册容器相关类型。这样容器错误可以复用原版验证器已有的能力：分类按钮、结果列表、世界方框高亮、HUD 坐标列表和选择状态。

验证每个方块时，`LitematicaSchematicVerifierMixin` 在原版 block state 检查之后追加容器检查：

1. 如果原理图当前位置不是 Inventory，就跳过。
2. 如果能读取实际库存，就比较并生成 `ContainerMismatch`。
3. 如果服务器数据还没准备好，就把位置放入 `pendingContainerPositions`。
4. 如果生成了错误，就存入 `containerMismatches` 和 `containerMismatchesByKey`。
5. 如果没有错误，就移除该位置旧的容器错误。

`ContainerMismatch` 会再包装成 Litematica 原版 `BlockMismatch`。`LitematicaBlockMismatchMixin` 给这个 `BlockMismatch` 挂上额外数据：原理图库存、实际库存、禁用槽、容器错误 key。列表、悬浮预览和选择恢复都靠这份附加数据。

## 验证器界面和右下角 HUD

验证器界面会额外添加容器错误分类按钮，并在底部显示：

`错误 / 缺失 / 状态 / 已检查 / 总容器数 / 待读取`

当结果模式是全部时，容器错误会作为单独分组插入原版结果列表，标题是“容器验证错误”。右下角 HUD 坐标列表也会把容器错误单独分段显示，坐标颜色来自 `QuickLitematicaVerifierPalette`，所以它和世界里高亮框、列表项颜色保持一致。

## 选择某一个容器后为什么会单独高亮

用户在验证器列表里选择某个容器错误时，Litematica 原版会把对应 `BlockMismatch` 加入 `selectedEntries`。QuickCraft 监听这个选择动作，并把容器错误同步到 `selectedContainerMismatches`。

刷新最近错误位置时：

- 如果选中了整个容器分类，就把该分类所有容器位置加入高亮列表。
- 如果只选了某一条列表项，就只从 `selectedEntries` 找到这个容器的位置。
- 最后把这些位置追加到 Litematica 原版 `mismatchPositionsForRender`。

世界里真正画框仍由 Litematica 原版渲染逻辑完成。QuickCraft 做的是把容器错误伪装成原版 `MismatchRenderPos`，并给它注册了对应颜色。

## 列表项悬浮时的左右库存预览

鼠标悬浮在容器错误列表项上时，`LitematicaWidgetSchematicVerificationResultMixin` 会拦截原版悬浮渲染，调用 `QuickLitematicaContainerVerifier.renderInventoryPair`。

这个预览分左右两侧：

- 左侧：原理图期望库存。
- 右侧：实际世界库存。

右侧会按出错槽位画底色和边框。缺失物品还会画半透明虚影，表示这个槽位应该放什么。颜色仍然来自统一调色板。

## 打开容器后的实时槽位高亮

玩家右键打开容器时，`LitematicaClientPlayerInteractionManagerMixin` 会记录最近一次成功交互的方块位置。容器界面开始渲染槽位时：

1. `LitematicaHandledScreenSlotOverlayMixin` 在每个槽位的 `drawSlot` 前后请求 `getSlotOverlayForScreen`。
2. `QuickLitematicaContainerVerifier` 把当前屏幕绑定到刚才记录的容器位置。
3. 每个 tick 或屏幕槽位 revision 变化时，复制当前容器界面内非玩家背包槽位。
4. 用这个实时库存调用 `quickcraft$refreshContainerMismatchAt` 刷新验证器里的同一位置。
5. 根据比较结果生成 `SlotOverlay`，在槽位上画底色、边框和缺失物品虚影。

因此打开容器后，槽位提示不是只看旧验证结果，而是会随着容器界面里的真实物品变化刷新。
其中“刷新验证结果”只依赖容器验证总开关；槽位提示开关只决定是否绘制视觉提示，不影响补对后自动取消世界高亮。

为了避免两套提示叠在一起，当容器验证槽位提示正在接管时，会临时取消 Litematica 原版材料 HUD 的槽位提示。

## 补对后为什么会自动取消高亮

自动取消高亮的核心在 `quickcraft$replaceContainerMismatchesAt`。

当容器被重新检查时，如果该位置已经没有任何槽位错误，新的 mismatch 列表就是空列表。此时逻辑会：

1. 移除该位置旧的 `ContainerMismatch`。
2. 从容器错误 map 中删掉旧 key。
3. 更新 Litematica 原版 mismatch overlay。
4. 如果该位置原来被选中，但现在没有新 mismatch 可以恢复选择，就不会再加入 `selectedEntries`。

所以补对以后，世界里的容器高亮框、验证器列表项、右下角 HUD 坐标和打开容器时的槽位高亮都会随下一次刷新消失。

这个刷新可能来自两条路径：

- 打开容器界面时，槽位 revision/tick 变化会即时刷新。
- 不打开容器时，验证器后台 tick 只复查 pending 位置，等服务器异步 NBT 数据回来后完成首次比较。

如果服务器数据还没读到，位置会保持待读取；只有读到了实际库存并确认正确，才会从 pending 中移除。已经查出来的错误容器不会被后台固定轮询；玩家打开并修改该容器时，会只刷新这个容器，或者重新点一键验证来全量刷新。

## pending 的含义

`pending` 不是“验证失败”，而是“当前还不能可信地比较库存”。常见原因：

- 多人服 Servux/OP 数据还没返回该位置的 BlockEntity NBT。
- 返回了 NBT，但该容器使用特殊字段，需要专门解析。
- 实际世界该位置暂时拿不到对应 BlockEntity。

近期已处理的特殊情况包括：

- 空容器 NBT 只有 `x/y/z/id`，没有 `Items`，现在会按空库存处理。
- 唱片机 NBT 使用 `RecordItem`，现在会解析成 1 槽库存。
- 实际位置已经不是容器块时，不再继续 pending，而交给原版方块状态错误处理。

## 调试日志怎么看

容器验证日志使用 `QuickCraft-ContainerVerifier` logger。关键字段：

- `expected`：本轮发现的原理图容器总数。
- `checked`：已经能完成库存比较的位置数。
- `pending`：还在等可靠实际库存的位置数。
- `wrong`：当前容器错误总数。
- `cacheBE`：Litematica/Servux 缓存里的 BlockEntity 数量。
- `actual(...)`：实际库存读取失败分类。
- `pending samples`：pending 数量较小时输出坐标和最后一次失败原因。

看到 `servux=true` 只代表通道存在，不代表每个容器都已经能比较。真正判断要看 `pending samples` 里是 `NO_CACHE_NBT`、`CACHE_WITHOUT_ITEMS`、`CACHE_PARSE_FAILED`、`foundBlockEntityMissing`，还是尺寸不匹配。
